# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

RestreamByDDas is a Django app for managing RTMP/SRT restream targets — i.e. a list of social media destinations (name, viewing URL, RTMP ingest URL, RTMP stream key) that a stream should be pushed to. Ingest/relay is implemented via separate Docker-built components (nginx-rtmp for RTMP, MediaMTX for SRT) that talk back to Django over HTTP hooks — see Architecture below.

The codebase is a small Django project: an `accounts` app (custom user model + admin-approval registration flow) and a `crud` app (owner-scoped stream configuration + the hook endpoints the RTMP/SRT infra calls).

## Product vision (target state)

- **RTMP first, SRT later (both implemented)**: RTMP shipped first; SRT ingest was added once RTMP was feature-complete, as an alternate front-door into the exact same RTMP pipeline (see Architecture — `srt-gateway/`/`srt-bridge/`). SRT destinations/push were never in scope — social platforms take RTMP for restream targets, so `Rtmp` destinations stay RTMP-only regardless of ingest protocol.
- **Non-standard auth (implemented)**: registration is not self-service. A new signup creates an inactive `PENDING` user and emails every `is_staff` user a confirm/reject link (`accounts` app); once an admin decides via that link, the user gets an email with the result. See Architecture below for how this is wired.
- **Per-user restream config (implemented)**: a logged-in user creates any number of `Stream` ingest points, and for each one specifies one or more `Rtmp` restream destinations (typically social media RTMP publish URLs/keys). Each destination has a user-assigned name (`socialmedia_name`). See Architecture below.
- **RTMP ingest + relay (implemented)**: users actually stream in and get relayed out — see Architecture below.
- **Stream statistics + server load (implemented)**: see Architecture below.
- **Broadcast restart (implemented)**: see Architecture below (`nginx_control.py`) — it's a full reset (drop the publisher, rely on the client reconnecting), not just relaunching the relay.
- **Deployment target (implemented locally)**: `docker-compose.yml` wires Django+Postgres+nginx together — see Architecture below. Production hardening (gunicorn instead of `runserver`, TLS, whitenoise) is intentionally not done yet.

## Commands

Dependencies are managed with Poetry; the virtualenv is created in-project at `.venv` (see `poetry.toml`).

```bash
poetry install                                    # install dependencies
poetry run python manage.py runserver             # run the dev server
poetry run python manage.py migrate                # apply migrations
poetry run python manage.py makemigrations <app>   # create a migration after model changes (e.g. crud, accounts)
poetry run python manage.py test                   # run the full test suite
poetry run python manage.py test crud               # run tests for one app only (accounts, crud)
poetry run python manage.py test crud.tests.<TestCase>.<test_method>  # run a single test
poetry run black .                                  # format code (black is a declared dependency)

docker compose up -d --build                        # run the full stack (nginx + django + postgres)
docker compose logs -f django                        # follow Django logs (incl. console-backend emails)
docker compose exec django python manage.py <cmd>    # run a management command inside the container
docker compose down -v                                # stop and wipe compose volumes (postgres data, static files)
```

A `.env` file (see `.env_example` for the required keys) must exist before running any `manage.py` command, since `config/settings.py` loads env vars via `python-dotenv` and reads `SECRET_KEY`, `FIELD_ENCRYPTION_KEY` (separate key for `crud.fields.EncryptedCharField`, see below — required for anything touching `Rtmp.socialmedia_rtmp_key`, including the test suite), `DEBUG`, `ALLOWED_HOSTS` (comma-separated), `DB_NAME`/`DB_USER`/`DB_PASSWORD`/`DB_HOST`/`DB_PORT` for PostgreSQL, and optional `EMAIL_*`/`DEFAULT_FROM_EMAIL`/`RTMP_SERVER_HOST`/`RTMP_APP`/`RTMP_HOOK_SECRET`/`NGINX_STAT_URL`/`NGINX_CONTROL_URL`/`SRT_SERVER_HOST`/`SRT_PORT`/`USE_TLS`/`YOUTUBE_API_KEY` vars (see below). There is no fallback/default DB — Postgres must be reachable for any command that touches models. `.github/workflows/ci.yml` runs `black --check`, `migrate`, `collectstatic`, then `test` on every push/PR against a fresh `postgres:16-alpine` service container — env vars are set directly as GitHub Actions `env:` (not a checked-in `.env`; `load_dotenv(override=True)` only matters when a `.env` file is actually present, which it isn't in a clean CI checkout since it's gitignored). `collectstatic` has to run before `test`: Django's test runner forces `DEBUG=False` for the run regardless of the env var, and `ManifestStaticFilesStorage` (see Static files below) requires a real manifest once DEBUG is off, or any template using `{% static %}` throws.

**Email in dev**: leave `EMAIL_HOST` unset in `.env` and outgoing mail (registration/approval notices) prints to the console instead of requiring SMTP.

**Note on `AUTH_USER_MODEL`**: it points at `accounts.User`. If you ever need to reset the dev DB after model changes to `accounts`, remember Django cannot swap `AUTH_USER_MODEL` on top of an already-migrated default `auth.User` — drop and recreate the dev database rather than trying to migrate in place.

**One `.env` for both bare-metal and Docker Compose**: values that differ between the two (`DB_HOST`, `ALLOWED_HOSTS`) are overridden per-service in `docker-compose.yml` rather than requiring a second env file — don't add a `DB_HOST=db`/`ALLOWED_HOSTS=...,django` to `.env` itself, that would break plain `manage.py runserver`.

## Architecture

- `config/` — the Django project package: `settings.py`, root `urls.py`, `wsgi.py`/`asgi.py`. `ROOT_URLCONF` points here and includes app URLs under path prefixes (`accounts/`, `crud/`).
- `accounts/` — custom user model and the admin-approval registration flow:
  - `models.py` — `User(AbstractUser)` with `approval_status` (`pending`/`approved`/`rejected`), `approved_at`. This is `AUTH_USER_MODEL`. (No `approved_by` — the approve/reject link works without login, so there's no admin identity to attribute the decision to; a field for it existed briefly but was always `None` and got removed.) Also `log_retention_days` (default `DEFAULT_LOG_RETENTION_DAYS = 5`, bounded 1–90 via validators) — per-user setting for how long `crud/management/commands/cleanup_destination_logs.py` keeps that user's destination log files (see `crud/` below); the module-level constant exists so the cleanup command's fallback for orphaned files (deleted destination/stream — no owner left to ask) can import the same default instead of duplicating the number.
  - `views.py` — `profile` (`accounts:profile`, login-required) is the user's account page — shows username/email (read-only) and a form for `log_retention_days` (`LogRetentionForm` in `forms.py`), PRG pattern (POST → `messages.success` → redirect) matching the rest of the app. `ProfilePasswordChangeView` subclasses Django's built-in `PasswordChangeView` (already `login_required` internally) just to add a success message and redirect straight to `accounts:profile` instead of a separate "done" page. Linked from `crud/base.html`'s topbar (username is now a link, not plain text). `register` creates an inactive `PENDING` user and emails admins, throttled per-IP the same way as login (`REGISTER_THROTTLE_LIMIT`/`_WINDOW` — a successful registration notifies every `is_staff` user, so an unthrottled endpoint is an admin-inbox spam vector, not just a form-abuse one); `admin_decision` handles the approve/reject link (GET shows a confirmation page, POST applies the decision) keyed by a signed token from `tokens.py` (`django.core.signing`, no login required to act on the link — the token itself is the credential, `max_age` bounds its lifetime). `ThrottledLoginView` wraps `LoginView` with a per-IP failed-attempt lockout (`LOGIN_THROTTLE_LIMIT`/`_WINDOW` constants, state in `django.core.cache` — default LocMemCache, so it's per-process; fine for the current single-worker deployment, won't share state across multiple gunicorn workers if that ever changes). All three throttles (login, register, password reset) key on `client_ip(request)`, not a bare `request.META["REMOTE_ADDR"]` — behind nginx (the only way this app is actually deployed, see docker-compose.yml notes below) `REMOTE_ADDR` is always nginx's own container IP, not the visitor's, so every real user would otherwise share one counter and one person's failed logins would lock out everyone else (confirmed live: same `REMOTE_ADDR` for requests carrying different `X-Forwarded-For` values). `client_ip()` trusts nginx's `X-Real-IP` header only when `REMOTE_ADDR` itself is a private/reserved address (Python's `ipaddress.is_private`, which covers RFC1918 *and* IANA special-purpose ranges) — i.e. only when the immediate connection came from inside the docker network — because `django`'s port is also published directly to the host (`8000:8000`) and a request hitting that port straight from the public internet could otherwise forge `X-Real-IP` to dodge the limit or frame another IP for it.
  - `emails.py` — sends the three notification emails (new-registration to all `is_staff` users, approved/rejected to the applicant) via `django.core.mail.send_mail` + templates under `accounts/templates/accounts/email/`.
  - Login/logout reuse Django's built-in `auth.views.LoginView`/`LogoutView` (the former subclassed as `ThrottledLoginView`, see above); a `PENDING`/`REJECTED` account simply can't log in because `is_active=False` until approved — no custom auth backend needed. Password reset also reuses Django's built-in `PasswordReset*View`s (`urls.py`) — each needs an explicit `success_url=reverse_lazy("accounts:...")` because their defaults resolve unnamespaced view names (`password_reset_done` etc.) that don't exist under this project's `app_name = "accounts"` namespacing and 404 otherwise. `PasswordResetView` is subclassed as `ThrottledPasswordResetView` (same per-IP cache pattern, `PASSWORD_RESET_THROTTLE_LIMIT`/`_WINDOW`) — counts every POST, not just ones for a registered email, since `PasswordResetForm` always responds the same way either way (deliberately, to not leak which emails exist), so "did it succeed" isn't a signal available here the way it is for login/register.
- `crud/` — two-level, owner-scoped RTMP configuration, plus the HTTP hooks nginx-rtmp calls:
  - `models.py` — `Stream` (an ingest point: `owner` FK to `accounts.User`, `name`, unique auto-generated `stream_key` shared by both protocols, `publish_server`/`srt_publish_url` properties built from `settings.RTMP_SERVER_HOST`/`RTMP_APP` and `settings.SRT_SERVER_HOST`/`SRT_PORT` respectively — either is `None` if its host setting is unset. `publish_server` deliberately excludes `stream_key` (`stream_detail.html` shows it as a separate "Ключ" field) — most encoders, OBS included, want "Server" and "Stream Key" as two fields to paste in, not one combined URL; `srt_publish_url` stays a single combined string since that's how SRT output fields are configured (one URL, `streamid=publish:<stream_key>` embedded as a query param, not a separate field anywhere); `Rtmp` (a restream destination: `stream` FK to `Stream`, social network name/viewing URL/RTMP link/RTMP key, `push_url` property = link+key joined for ffmpeg). `socialmedia_rtmp_key` is a real credential (the platform's stream key), so it's stored encrypted at rest via `crud.fields.EncryptedCharField` (Fernet, key in `settings.FIELD_ENCRYPTION_KEY`, separate from `SECRET_KEY` so one can be rotated without the other) — see `crud/fields.py`. Fernet isn't deterministic (same plaintext → different ciphertext each time), so there's no DB-level `unique`/`unique_together` on this field and no `.filter(socialmedia_rtmp_key=...)` anywhere; per-stream uniqueness is enforced in `Rtmp.clean()` by decrypting and comparing in Python — on the **model**, not in `DestinationForm`, because a form-level check is invisible to any other `ModelForm` built from this model, and Django admin builds its own (`RtmpAdmin` doesn't set `form =`); confirmed live that duplicates saved silently through `/admin/crud/rtmp/add/` before this moved to `Model.clean()` (which every `ModelForm`, admin's included, calls via `full_clean()`). `destination_create`/`destination_update` wrap the check+save in `transaction.atomic()` with `Stream.objects.select_for_update()` to close the race a DB constraint would otherwise have closed — admin's own add/change views aren't wrapped the same way, which is an accepted narrower gap (staff-only, not the main user-facing path). Migration `crud.0004_...` re-saves every existing row to encrypt values written before this field existed — safe to re-run/idempotent because `from_db_value` falls back to returning a value as-is (via `InvalidToken`) when it isn't a valid Fernet token, so reading pre-migration plaintext never crashes. `Rtmp.platform_badge` (property, matched by substring against `socialmedia_name` — free text, not a choice field) drives the colored circular initials-badge next to each destination on `stream_detail.html` — deliberately not the platforms' actual logos/SVGs (trademark-fidelity concerns not worth it for a decorative badge); unrecognized platform name falls back to its first letter on a neutral gray badge rather than erroring or showing nothing.
  - `views.py` (CRUD) — all require login (`@login_required`) and scope queries to the current user (`Stream.objects.filter(owner=request.user)`, `Rtmp` via `stream__owner=request.user`); accessing another user's object returns 404 rather than 403 to avoid leaking existence. `destination_log` (`crud:destination_log`) is the same pattern applied to log viewing — reads `crud/destination_logs.py`'s `read_destination_log(stream_key, destination_id)`, which just does a filesystem read against the shared `rtmp_logs` volume (see `rtmp-push/` above); no separate auth layer needed since the file path is built from already-owner-checked `Rtmp`/`Stream` fields, not raw request input. Tail-capped to the last 500 lines (`MAX_LINES`) to keep the page bounded regardless of how long a destination has been erroring/reconnecting.
  - `views.py` (infra hooks, called by nginx/`rtmp-push`/MediaMTX, not browsers — all under the `rtmp-hooks/` URL prefix even though `srt_auth_hook` now lives there too) — `on_publish_hook` (`crud:on_publish_hook`) validates a stream_key on RTMP publish start (200/403); `stream_destinations_hook` (`crud:stream_destinations_hook`) returns a JSON list of `push_url`s for `rtmp-push/push.sh` to relay to (only `Rtmp.enabled=True` destinations — the per-destination toggle switch on `stream_detail.html`, `crud:destination_toggle`, POST-only, owner-checked, just flips the field; like the rest of the destination list, only takes effect on the next publish start, not a currently-live one — see the restart hint on that page); `srt_auth_hook` (`crud:srt_auth_hook`) is MediaMTX's `authHTTPAddress` target — JSON body (not form-encoded like the others), always allows non-`"publish"` actions, validates `path` against the DB for `"publish"`; `destination_status_hook` (`crud:destination_status_hook`) is `rtmp-push/push.sh`'s callback for per-destination push status (see `rtmp-push/` below). All four require `?secret=` to match `settings.RTMP_HOOK_SECRET` via `hmac.compare_digest` (not `==` — constant-time, avoids a timing side-channel on the shared secret) (shared across RTMP and SRT infra; empty secret = always reject, fail closed).
  - `nginx_stat.py` — `fetch_stream_stats(stream_key)` pulls and parses nginx-rtmp's `/stat` XML (`settings.NGINX_STAT_URL`, empty = skip and return `None` — e.g. bare dev with no nginx running). Returns `None` (unavailable), `{"live": False}` (not currently streaming), or live byte/bitrate/uptime counts plus (`_parse_meta`) the incoming stream's own technical parameters — resolution, frame rate, video codec, audio codec/channels/sample rate — read from nginx-rtmp's `<meta>` block in `/stat` (nginx itself parses this from the publisher's `onMetaData`/codec headers, not something this project computes). Keys are simply absent from the dict (not `None`) when `<meta>` isn't there yet — briefly true right after publish start, before nginx has had a chance to parse it — so template/JS only need one falsy check (`stats.video_codec`), not a None-vs-missing distinction. Used by `stream_detail` to show per-stream status and, when present, this media info as a second row under the byte/bitrate stats.
  - `server_load.py` — `get_server_load()`: `os.getloadavg()` (always available on Linux/macOS), memory % from `/proc/meminfo` and disk % from `shutil.disk_usage("/")` (both `None` if unreadable, e.g. no `/proc` outside Linux — degrades per-metric, not as an all-or-nothing block). Used by `index` for a "server load" panel; inside the Docker containers this reflects real container/host figures, on bare macOS dev memory is `None` but load/disk still populate.
  - `nginx_control.py` — `restart_stream(stream_key)` calls nginx-rtmp's control module (`GET /control/drop/publisher`, `settings.NGINX_CONTROL_URL` + `settings.RTMP_APP`, empty URL = unavailable, same fail-closed pattern as the other nginx integrations) to forcibly disconnect the current publisher. This is a full reset, not a relay-only restart — it only "restarts the broadcast" if the streaming client (OBS etc.) auto-reconnects, which then runs the normal `on_publish`/`exec_publish`/`push.sh` cycle again (picking up any destination changes). `crud:stream_restart` is the login-required, owner-checked, CSRF-protected view wiring this to a button on `stream_detail`; result surfaces via `django.contrib.messages` (first use of that framework in the project — already configured, just unused before). `stream_delete` calls the same `restart_stream()` right after deleting the row — confirmed live that without it, a publisher nginx had already accepted keeps relaying to every destination completely unaffected by the DB delete (nginx never re-checks a live publish against the DB mid-stream; only a *new* publish attempt hits `on_publish_hook` and gets rejected), so "delete" alone didn't actually stop an in-progress broadcast.
  - `checks.py` — Django system checks (`crud.E001`/`E002`/`E003`), registered from `CrudConfig.ready()`, run automatically on every management command including `migrate` (the first thing `docker-entrypoint.sh` runs). Exist because both failure modes they catch otherwise pass an empty install silently and only surface later, cryptically: a missing/invalid `FIELD_ENCRYPTION_KEY` doesn't error until the first `Rtmp` row is actually read/written (`Fernet(...)` in `crud/fields.py` is only ever called lazily, not at import time), and an empty `ALLOWED_HOSTS` with `DEBUG=False` doesn't error until the first real request (Django only enforces it via `DisallowedHost` at request time, not at startup) — which for this project includes the nginx/srt hooks, so it silently breaks 100% of publishing, not just the web UI. Added after a real deployment (hand-rolled `docker-compose.yml` instead of using `docker-compose.prod.yml`) hit both blind.
  - **Multi-chat (YouTube, first of a planned multi-platform set)** — `youtube_chat.py` (thin `urllib.request` wrapper around YouTube Data API v3: `fetch_live_chat_id(video_id)` resolves `liveStreamingDetails.activeLiveChatId` from the video, `fetch_new_messages(live_chat_id, page_token)` polls `liveChat/messages`) uses a single server-level `settings.YOUTUBE_API_KEY` — **not per-user OAuth** — because reading a public live chat's messages only needs an API key, not authorization from the broadcaster; this is what keeps v1 scope-able (no OAuth token storage/refresh to build). `Stream.youtube_chat_video_id` (form-cleaned from either a raw ID or a pasted `youtube.com/watch?v=`/`youtu.be/` URL — `crud.forms.StreamChatForm.clean_youtube_chat_video_id` — hence the field's `max_length=200` even though the stored value is always an 11-char ID: Django's `ModelForm` runs the field's `max_length` validator on the *raw* submitted string before `clean_<field>()` ever gets a chance to shorten it) is set per-`Stream`, not per-`Rtmp` destination — chat belongs to "what's being broadcast into this stream_key right now", not to any one push-out direction, and matching `restream.su`'s framing of chat as one unified thing per broadcast rather than per-destination. `ChatMessage` (stream FK, `platform` choice for future VK/etc., `external_id` + `UniqueConstraint(stream, platform, external_id)` to survive YouTube occasionally redelivering a message across adjacent poll pages).
    - `crud/management/commands/poll_youtube_chat.py` is the project's first-ever **long-running** process — everything else here is either a one-shot HTTP hook or `cleanup_destination_logs`'s hourly re-exec (fresh process, fresh DB connection, every time). This command is a single `while True` loop, started once by `docker-entrypoint.sh` and never re-launched unless it crashes (wrapped in its own restart-on-crash shell loop there, since a bare Python exception would otherwise silently kill chat polling until the container itself restarts). Per-stream polling state (`live_chat_id`, YouTube's `nextPageToken`, `next_poll_at` honoring YouTube's own `pollingIntervalMillis`) lives in a plain in-process dict, not the DB — it's only meaningful for the lifetime of this process anyway, no need to persist/recover it across restarts. Because the DB connection is held open for the process's entire lifetime (unlike every other management command in this project), it explicitly catches `django.db.OperationalError` and calls `connection.close()` to force a reconnect — Django's usual "close stale connections" machinery only hooks into the request/response cycle, which a bare infinite-loop command never goes through.
    - `crud:stream_chat_json` mirrors `stream_stats_json`'s incremental-polling shape (`live_stats.js`'s `pollChat()`, 3s interval) but keyed by `after_id` (last message's PK) instead of a live/not-live flag — first load returns the last 50 messages, subsequent polls return only `pk__gt=after_id`. Message text is inserted into the DOM via `textContent`/`createElement`, not `innerHTML` string concatenation — chat author names and message text are third-party-controlled strings (from YouTube), the one piece of user-adjacent content in this JS file that isn't already Django-escaped server-side. `crud:stream_chat_reset` clears both `Stream.youtube_chat_video_id` *and* deletes all of that stream's `ChatMessage` rows together, not just the source setting — leaving old messages around would otherwise mix a since-ended broadcast's chat in with whatever gets connected next. Only rendered on `stream_detail.html` when a video ID is currently set (nothing to reset otherwise); confirms via a plain JS `confirm()` since it's destructive and has no undo. Disconnecting isn't only possible through that button, though — `stream_chat_settings` (the "Сохранить" form) also clears message history whenever the *new* value is empty, and `stream_chat_json` independently refuses to return any messages at all whenever `youtube_chat_video_id` is empty regardless of what's still in the DB — confirmed live that without these, disconnecting via "Сохранить" with a blank field (as opposed to the dedicated "Сбросить" button) left old messages both in the DB and stuck rendered in already-open tabs forever, since the JS poller's `tick()` used to silently no-op whenever a poll returned zero *new* messages rather than checking `chat_enabled` and clearing what was already drawn.
    - VK is intentionally not implemented yet — its third-party API access landscape shifted in 2025/2026 (the old general `api.vk.com` third-party access got restricted; a distinct **VK Video Live DevAPI**, `dev.live.vkvideo.ru`, opened for stream tooling including chat around March 2025) and its docs site is a JS SPA this project's tooling can't fetch to verify exact auth/endpoints — implement it once those specifics are confirmed directly, not from memory/secondhand summaries. Also unconfirmed: whether this project's VK destinations target classic VK Live (`vk.com`) or VK Video Live (`vkvideo.ru`) — they may not be the same broadcast/chat.
- `nginx/` — Docker image for nginx-rtmp (not installable as a stock package; built from `debian:bookworm-slim` + the `libnginx-mod-rtmp` apt package, which bundles both the stat and control sub-modules — no separate module needed for `/control`). `nginx/conf/nginx.conf.template` is rendered by `nginx/docker-entrypoint.sh` via `envsubst` (`DJANGO_HOOK_BASE_URL`, `RTMP_HOOK_SECRET` env vars) before nginx starts. Build from the **repo root** (not `nginx/`) so the build context includes `rtmp-push/`: `docker build -f nginx/Dockerfile -t restream-nginx .`. Deliberately `worker_processes 1` — nginx-rtmp connections/stats aren't shared across workers, so `/stat` on a multi-worker setup only reflects whichever worker handled a given request. The internal `server { listen 8080; }` block hosts both `/stat` and `/control` (`rtmp_control all;`) — not published beyond `127.0.0.1` on the host, same trust boundary for both. `nginx/docker-entrypoint.sh` also `chmod 1777`s `/tmp/rtmp-push` (the `rtmp_logs` volume's mount point, see `rtmp-push/` below) before starting nginx — that path is now a named Docker volume, not a plain `/tmp` subdirectory, and Docker initializes a fresh volume's root as `root:root 0755`; `exec_publish`/`exec_publish_done` (`push.sh`/`stop.sh`) run as the nginx worker's user (`www-data`, not root — `user www-data;` above), so without this fix `push.sh`'s first line (`mkdir -p "$PID_DIR"`) fails `Permission denied` and the *entire* restream-out mechanism silently stops working — not just log viewing. Confirmed live on a real deployment: nginx's own log showed `exec: child '/rtmp-push/push.sh' started` immediately followed by `exited with code 1`, no error visible anywhere else (default nginx `error_log` level doesn't surface either line — had to temporarily bump to `debug` to see it at all). A real regression from introducing the `rtmp_logs` volume for `crud:destination_log`, not a pre-existing issue.
- `rtmp-push/` — `push.sh`/`stop.sh`, invoked by nginx-rtmp's `exec_publish`/`exec_publish_done` (not run directly). `push.sh` fetches the destination list from `stream_destinations_hook` and launches **one `ffmpeg -c copy` process per destination** (not one process with N `-f flv` outputs — confirmed live that ffmpeg aborts the *entire* process if it can't open even one of several outputs, which was silently killing delivery to every destination whenever just one was unreachable), tracking each PID at `/tmp/rtmp-push/<stream_key>/<destination_id>.pid` (and its own `<destination_id>.log`, kept around after the stream ends — only the `.pid` is removed — so a failed destination is still debuggable after the fact; a subsequent publish for the same `stream_key` just overwrites the same destination-keyed files). Filenames are keyed by the destination's DB id (not its position in the list) so they stay stable regardless of destination order/count between publishes — `crud:destination_log` (see below) depends on this being a fixed, predictable key. This dir is a named Docker volume (`rtmp_logs`, see `docker-compose.yml` below) shared into the `django` container at `/rtmp-logs` — not read-only, since `crud/management/commands/cleanup_destination_logs.py` (run hourly by `docker-entrypoint.sh` in the background, plus once at container start) needs to delete stale `*.log` files there; it only ever touches `.log`, never `.pid`, on purpose — `.pid` bookkeeping is `push.sh`/`stop.sh`'s alone, Django doesn't get to touch a live process's control file. For a still-existing destination, retention is its owner's `accounts.User.log_retention_days`; for an orphaned file (destination or whole stream already deleted from the DB — nobody left to own a retention setting) it falls back to `accounts.models.DEFAULT_LOG_RETENTION_DAYS`, which also incidentally fixes the "deleted destination's log lingers forever" gap this file layout used to have. `crud:destination_log`'s template shows the current retention via `crud/templatetags/ru_plural.py`'s `ru_days` filter — Django's built-in `|pluralize` only handles English-style singular/plural and silently renders empty for the 3-way Russian день/дня/дней (confirmed live), so this is a real custom filter, not decoration. Builds the ffmpeg argv via `set --` rather than `eval`/`sh -c` on purpose — destination URLs/keys come from user input (`Rtmp` fields) and must never be shell-interpreted (command injection). `stop.sh` sends TERM then polls `kill -0` for up to 5s before escalating to KILL, logging if it had to, for *each* per-destination process — nginx-rtmp doesn't force-close the push ffmpeg's read side when the publisher disconnects (it just goes idle), and a plain TERM confirmed live to sometimes never take effect, leaving the process stuck with an established connection to the destination indefinitely (discovered via live end-to-end testing with a real destination listener, reproduced twice). Each destination also gets its own background subshell in `push.sh` that reports live/error/stopped status back to Django (`crud:destination_status_hook`, `?destination_id=&status=`) — `Rtmp.push_status`/`push_status_at`, surfaced as a badge next to the destination's name on `stream_detail.html`, but **only while the stream itself is live** per nginx's `/stat` (guards against a stale "live"/"error" badge lingering in the DB from a session where nginx died uncleanly before it could report the real end state — Django has no other way to know the push processes' live status, unlike the stream-level badge which re-queries `/stat` fresh on every page load). The subshell distinguishes "stopped" (its own ffmpeg was killed by `stop.sh` — `wait` returns exit code 143/137, a signal) from "error" (ffmpeg exited on its own for any other reason — couldn't connect, or the destination dropped the connection mid-stream) purely from the exit code, no extra signaling needed between `push.sh` and `stop.sh`. `stream_destinations_hook`'s JSON now includes each destination's `id` (not just `push_url`) so `push.sh` has something to key status reports on.
- `srt-gateway/` — Docker image for SRT ingest, built on `bluenviron/mediamtx` (pinned release binary — `MEDIAMTX_VERSION` build arg in `srt-gateway/Dockerfile`, downloaded from GitHub releases for `$TARGETARCH`, not installable as a stock package either) + `ffmpeg`. **Key design point**: SRT is not a parallel stack with its own destinations/stats/restart — MediaMTX is just an alternate front door into the *same* RTMP ingest nginx already has. A client publishes SRT with `streamid=publish:<stream_key>` (same `stream_key` as RTMP — one ingest point, either protocol); MediaMTX's `authHTTPAddress` hits `crud:srt_auth_hook` (validates `action=="publish"` against the DB, same `RTMP_HOOK_SECRET`, always allows non-publish actions since our own bridge's internal read would otherwise get gated too); `paths.all_others.runOnReady` launches `srt-bridge/start.sh`, which reads the stream back from MediaMTX's own built-in RTMP re-exposure (`rtmp://127.0.0.1:1935/<path>`) and republishes with `-c copy` into nginx's `rtmp://nginx:1935/live/<stream_key>` — from that point on it's an ordinary RTMP publish and 100% of the existing pipeline (`on_publish_hook`, `push.sh`, destinations, `/stat`, restart) applies unchanged, no SRT-specific code anywhere downstream.
  - `srt-bridge/start.sh` runs in the **foreground** (`exec ffmpeg ...`, no backgrounding/PID file) — MediaMTX manages its lifecycle directly and sends it a stop signal when the path stops being ready (visible as "runOnReady command stopped" in `srt-1` logs), so there's no `stop.sh` needed (unlike `rtmp-push/`, where nginx's `exec_publish`/`exec_publish_done` are two separate hooks). `runOnReadyRestart: yes` in `srt-gateway/conf/mediamtx.yml.template` auto-relaunches the bridge if it fails to connect on the first try. **Do not turn `start.sh` into a backgrounding script again** — combined with `runOnReadyRestart` that caused MediaMTX to relaunch it every few seconds while the old ffmpeg process kept running in the background, spawning duplicate publishers (discovered live: repeated "runOnReady command exited: code 0" every ~5s in `srt-1` logs).
  - `-probesize 5000000 -analyzeduration 5000000` on the bridge's ffmpeg input are required, not cosmetic — MediaMTX's RTMP re-exposure of a freshly-ingested SRT stream doesn't carry a reliable `onMetaData` (unlike a normal OBS→RTMP publish), so ffmpeg's default probing intermittently fails to determine codec parameters in time and the relay to nginx never completes before a short-lived stream ends. Confirmed via live testing: without these flags, short streams reliably failed to relay (`Cannot open connection tcp://nginx:1935`); with them, short streams relay correctly.
  - Exact `runOnReady`/`authHTTPAddress` config key names were verified against the pinned MediaMTX version's own shipped `mediamtx.yml` (`docker run --rm <image> cat /mediamtx.yml`, or the raw file at that exact git tag) rather than assumed — MediaMTX has renamed hook directives across versions (older docs/AI summaries may reference `runOnOnline`/`runOnOffline` or `runOnPublish`, which do **not** exist in the pinned version). Re-verify against the shipped config if `MEDIAMTX_VERSION` is ever bumped.
  - **Known limitation**: `crud:stream_restart` (see `nginx_control.py` above) drops the RTMP-facing leg (the bridge) for SRT-sourced streams, not the original SRT connection at MediaMTX — the source stays connected there, but the relay into nginx won't come back until the SRT client itself reconnects. No MediaMTX-side "kick" is wired up (no API endpoint for this was confirmed reliable enough to implement blind).
- Templates live under `<app>/templates/<app>/` following Django's app-namespaced template convention. `crud/base.html` (nav bar + messages block, styled via `crud/static/crud/style.css`) is extended by every template in both `crud/` and `accounts/` — there's no project-level shared-template app, so `accounts/` templates cross-reference `crud/`'s on purpose rather than duplicating the stylesheet. `crud/base.html`'s nav checks `request.user`, not a bare `user` — some `accounts` views (e.g. `admin_decision_confirm`) pass their own `user` context variable (the account being approved/rejected, not the visitor), which would otherwise silently shadow the auth context processor's `user` and make an anonymous visitor look logged in as whoever they're approving. `LANGUAGE_CODE = "ru"` (not the Django default `"en-us"`) so Django's own built-in strings (auth form labels/errors, password validators, etc.) come out in Russian via Django's stock translations, matching the rest of the UI, without hand-overriding form labels.
- `crud/context_processors.py` — `app_version(request)` puts `settings.APP_VERSION` into every template's context (registered in `TEMPLATES` → `context_processors` in `config/settings.py`), so `crud/base.html`'s footer (`RestreamByDDas {{ app_version }}`) can show it on every page without every view passing it explicitly. `APP_VERSION` itself is build-time metadata, not a user setting — it comes from the Django image's `ENV APP_VERSION` (set in `Dockerfile` from `ARG APP_VERSION=dev`), which `.github/workflows/docker-publish.yml` populates via `build-args: APP_VERSION=${{ github.ref_name }}` (the exact git tag, e.g. `v1.2.3`) when CI builds a release; a plain local `docker compose up --build` (no CI, no tag) falls back to the `dev` default. All three Dockerfiles also stamp the same value into `org.opencontainers.image.version` (visible via `docker inspect`, not just the footer) for consistency, though only the `django` image actually reads it back at runtime — `nginx`/`srt` don't serve any UI to show it in.
- `crud/static/crud/copy.js` — the project's first client-side JS: a single delegated click handler for `.copy-btn` (rendered via the `crud/_copy_field.html` include, used on `stream_detail.html`'s server/SRT/key rows), copying `data-copy` to the clipboard via `navigator.clipboard` with an `execCommand("copy")` fallback for non-secure contexts (`navigator.clipboard` needs HTTPS or localhost; this project doesn't serve HTTPS anywhere yet — see `USE_TLS` above). Loaded from `crud/base.html`, so available on every page even though only `stream_detail.html` uses it today. The copy icon's `<svg>` needs `flex-shrink: 0` in CSS — without it, an SVG with only a `viewBox` (no `width`/`height` attributes) collapses to 0px inside a flex container regardless of any CSS `width` set on it (confirmed live: icon was fully invisible, `getComputedStyle` reported `width: 0px`, until that one property was added).
- Static files: `STORAGES["staticfiles"]` is `ManifestStaticFilesStorage` (content hash in the filename, e.g. `style.<hash>.css`) so a redeploy can never serve a stale cached asset under the old URL — but Django deliberately skips the hash substitution in `{% static %}` while `DEBUG=True` (its own `HashedFilesMixin._url()`, not a bug here), so this only actually cache-busts once something runs with `DEBUG=False` (nothing does yet — see `USE_TLS` below). For the current `DEBUG=True` dev/compose setup, `nginx/conf/nginx.conf.template`'s `location /static/` sends `Cache-Control: no-cache` instead, forcing browsers to revalidate every load rather than trust a heuristic cache lifetime (confirmed live: without this, an edited `crud/style.css` kept rendering as the old version after a plain reload).
- Security settings gate on `USE_TLS` (env var), **not** `DEBUG` — `SESSION_COOKIE_SECURE`/`CSRF_COOKIE_SECURE`/`SECURE_SSL_REDIRECT`/HSTS only turn on when `USE_TLS=True`. Deliberately decoupled from `DEBUG`: TLS termination isn't wired up anywhere yet (see docker-compose.yml notes below), so tying these to `DEBUG=False` would let someone flip `DEBUG` off before TLS exists and silently break login (browser won't send a `Secure` cookie over plain `http://`) or redirect-loop to a nonexistent `https://`.
- `LOGGING` in `settings.py` is minimal (root logger → console) — added because `crud/nginx_stat.py` and `crud/nginx_control.py` used to swallow every connection failure with a bare `except: return None/False`, so a broken `/stat` or `/control` integration had zero trace anywhere. Both now `logger.warning(..., exc_info=True)` before returning the same fallback value — behavior is unchanged, only observability.
- `Dockerfile`/`docker-entrypoint.sh` (repo root) — the Django image (`python:3.13-slim` + Poetry, `POETRY_VIRTUALENVS_CREATE=false`, `poetry install --without dev` so the `black` dev-group dependency never ships in the image). The entrypoint waits for Postgres to accept connections (plain `depends_on` only waits for container start, not DB readiness), then runs `migrate`, `collectstatic`, `cleanup_destination_logs` once, spawns a background `while true; do sleep 3600; cleanup_destination_logs; done` loop (no Celery/task-queue in this project — this is the entire scheduler), spawns `poll_youtube_chat` in its own restart-on-crash background loop (see `crud/` → Multi-chat above — unlike the cleanup loop, this one command runs forever rather than being re-invoked periodically), and finally `runserver 0.0.0.0:8000`. `.dockerignore` excludes `.env` — never remove that exclusion, `COPY . .` would otherwise bake secrets into the image layer.
- `docker-compose.yml` — `db` (`postgres:16-alpine`, not exposed to the host to avoid clashing with a locally-running Postgres on 5432), `django` (builds the root `Dockerfile`; its `8000` is published as `127.0.0.1:8000:8000`, not `8000:8000` — nginx reaches it at `http://django:8000` over the compose network regardless of host port publishing, so this is purely for local `curl localhost:8000` convenience; publishing to `0.0.0.0` would let anyone reach Django directly on a real server, bypassing nginx and its `Cache-Control` — this is also why `accounts.views.client_ip()` can't blindly trust `X-Real-IP`, see above), `nginx` (builds `nginx/Dockerfile`, now also reverse-proxies HTTP: a second `server { listen 80; }` block in `nginx/conf/nginx.conf.template` proxies `/` to `http://django:8000` and serves `/static/` directly from a shared `static_files` volume populated by `collectstatic`; also writes `rtmp-push/push.sh`'s per-destination logs to the `rtmp_logs` volume at `/tmp/rtmp-push`, also mounted into `django` at `/rtmp-logs` — read/write there, not read-only, see `rtmp-push/` above for why), `srt` (builds `srt-gateway/Dockerfile`, exposes `8890/udp`). nginx's/MediaMTX's hooks reach Django at `http://django:8000` — Django's `ALLOWED_HOSTS` gets `django` appended in compose (see the `.env` note above) since that hostname never appears in the browser-facing `Host` header. `RTMP_SERVER_HOST`/`SRT_SERVER_HOST` (the *public* addresses shown to users) are deliberately **not** overridden in compose — they come straight from `.env`, same as on bare metal, since they mean something different (the box's public hostname/IP) than the compose-internal service hostnames used elsewhere in this file.
