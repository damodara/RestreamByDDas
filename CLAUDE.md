# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

RestreamByDDas is a Django app for managing RTMP/SRT restream targets — i.e. a list of social media destinations (name, viewing URL, RTMP ingest URL, RTMP stream key) that a stream should be pushed to. Ingest/relay is implemented via separate Docker-built components (nginx-rtmp for RTMP, MediaMTX for SRT) that talk back to Django over HTTP hooks — see Architecture below.

The codebase is a small Django project: an `accounts` app (custom user model + admin-approval registration flow) and a `crud` app (owner-scoped stream configuration + the hook endpoints the RTMP/SRT infra calls).

## Product vision (target state)

- **RTMP first, SRT later (both implemented)**: RTMP shipped first; SRT ingest was added once RTMP was feature-complete, as an alternate front-door into the exact same RTMP pipeline (see Architecture — `srt-gateway/`/`srt-bridge/`). SRT destinations/push were never in scope — social platforms take RTMP for restream targets, so `Rtmp` destinations stay RTMP-only regardless of ingest protocol.
- **Non-standard auth (implemented)**: registration is not self-service. A new signup creates an inactive `PENDING` user and emails every `is_staff` user a confirm/reject link (`accounts` app); once an admin decides via that link, the user gets an email with the result. See Architecture below for how this is wired.
- **Per-user restream config (implemented)**: a logged-in user creates any number of `Stream` ingest points, and for each one specifies one or more `Rtmp` restream destinations (typically social media RTMP publish URLs/keys). Each destination has a user-assigned name (`socialmedia_name`). See Architecture below.
- **RTMP ingest + relay (implemented)**: users actually stream in and get relayed out — see Architecture below.
- **Stream statistics + server load (implemented)**: see Architecture below.
- **Broadcast restart (implemented)**: see Architecture below (`nginx_control.py`) — it's a full reset (drop the publisher, rely on the client reconnecting), not just relaunching the relay.
- **Deployment target (implemented locally)**: `docker-compose.yml` wires Django+Postgres+nginx together — see Architecture below. Production hardening (gunicorn instead of `runserver`, TLS, whitenoise) is intentionally not done yet.

## Commands

Dependencies are managed with Poetry; the virtualenv is created in-project at `.venv` (see `poetry.toml`).

```bash
poetry install                                    # install dependencies
poetry run python manage.py runserver             # run the dev server
poetry run python manage.py migrate                # apply migrations
poetry run python manage.py makemigrations <app>   # create a migration after model changes (e.g. crud, accounts)
poetry run python manage.py test                   # run the full test suite
poetry run python manage.py test crud               # run tests for one app only (accounts, crud)
poetry run python manage.py test crud.tests.<TestCase>.<test_method>  # run a single test
poetry run black .                                  # format code (black is a declared dependency)

docker compose up -d --build                        # run the full stack (nginx + django + postgres)
docker compose logs -f django                        # follow Django logs (incl. console-backend emails)
docker compose exec django python manage.py <cmd>    # run a management command inside the container
docker compose down -v                                # stop and wipe compose volumes (postgres data, static files)
```

A `.env` file (see `.env_example` for the required keys) must exist before running any `manage.py` command, since `config/settings.py` loads env vars via `python-dotenv` and reads `SECRET_KEY`, `FIELD_ENCRYPTION_KEY` (separate key for `crud.fields.EncryptedCharField`, see below — required for anything touching `Rtmp.socialmedia_rtmp_key`, including the test suite), `DEBUG`, `ALLOWED_HOSTS` (comma-separated), `DB_NAME`/`DB_USER`/`DB_PASSWORD`/`DB_HOST`/`DB_PORT` for PostgreSQL, and optional `EMAIL_*`/`DEFAULT_FROM_EMAIL`/`SITE_URL`/`RTMP_SERVER_HOST`/`RTMP_APP`/`RTMP_HOOK_SECRET`/`NGINX_STAT_URL`/`NGINX_CONTROL_URL`/`SRT_SERVER_HOST`/`SRT_PORT`/`USE_TLS`/`YOUTUBE_API_KEY`/`TELEGRAM_BOT_TOKEN`/`TELEGRAM_BOT_USERNAME` vars (see below). There is no fallback/default DB — Postgres must be reachable for any command that touches models. `.github/workflows/ci.yml` runs `black --check`, `migrate`, `collectstatic`, then `test` on every push/PR against a fresh `postgres:16-alpine` service container — env vars are set directly as GitHub Actions `env:` (not a checked-in `.env`; `load_dotenv(override=True)` only matters when a `.env` file is actually present, which it isn't in a clean CI checkout since it's gitignored). `collectstatic` has to run before `test`: Django's test runner forces `DEBUG=False` for the run regardless of the env var, and `ManifestStaticFilesStorage` (see Static files below) requires a real manifest once DEBUG is off, or any template using `{% static %}` throws.

**Email in dev**: leave `EMAIL_HOST` unset in `.env` and outgoing mail (registration/approval notices) prints to the console instead of requiring SMTP.

**Note on `AUTH_USER_MODEL`**: it points at `accounts.User`. If you ever need to reset the dev DB after model changes to `accounts`, remember Django cannot swap `AUTH_USER_MODEL` on top of an already-migrated default `auth.User` — drop and recreate the dev database rather than trying to migrate in place.

**One `.env` for both bare-metal and Docker Compose**: values that differ between the two (`DB_HOST`, `ALLOWED_HOSTS`) are overridden per-service in `docker-compose.yml` rather than requiring a second env file — don't add a `DB_HOST=db`/`ALLOWED_HOSTS=...,django` to `.env` itself, that would break plain `manage.py runserver`.

## Architecture

- `config/` — the Django project package: `settings.py`, root `urls.py`, `wsgi.py`/`asgi.py`. `ROOT_URLCONF` points here and includes app URLs under path prefixes (`accounts/`, `crud/`).
- `accounts/` — custom user model and the admin-approval registration flow:
  - `models.py` — `User(AbstractUser)` with `approval_status` (`pending`/`approved`/`rejected`), `approved_at`. This is `AUTH_USER_MODEL`. (No `approved_by` — the approve/reject link works without login, so there's no admin identity to attribute the decision to; a field for it existed briefly but was always `None` and got removed.) Also `log_retention_days` (default `DEFAULT_LOG_RETENTION_DAYS = 5`, bounded 1–90 via validators) — per-user setting for how long `crud/management/commands/cleanup_destination_logs.py` keeps that user's destination log files (see `crud/` below); the module-level constant exists so the cleanup command's fallback for orphaned files (deleted destination/stream — no owner left to ask) can import the same default instead of duplicating the number. Also `notify_on_push_error` (`BooleanField`, default `False`) — opt-**in**, not opt-out: whether to email this user when one of their destinations' push fails (`crud.emails.send_push_error_email`, triggered from `crud.views.destination_status_hook`, see `crud/` below). Defaults off deliberately — a user who never asked for email alerts shouldn't start getting them just because a destination they haven't touched in months starts erroring. Also `telegram_chat_id` (blank = not linked) and `notify_telegram_on_push_error` (`BooleanField`, default `False`) — a second, independent opt-in for the same push-error event, not a single "pick one channel" choice: a user may want both email (as an archive) and Telegram (as an instant ping), or just one. `telegram_chat_id` is never set by the user directly — see `telegram_bot.py`/`poll_telegram_bot` below for how it gets populated. Also `auto_end_broadcast_on_drop` (`BooleanField`, default `False`) — governs what `crud.management.commands.poll_stream_health` does with a stream it finds gone from `/stat` while still `expected_live` and never explicitly ended (see `crud/models.py`'s `Stream.expected_live` below): default (`False`) treats it as an unannounced incident and notifies through the two toggles above; turning this on tells the server that a dropped signal alone already means "the broadcast is over" for this user, so it's cleared silently instead.
  - `views.py` — `profile` (`accounts:profile`, login-required) is the user's account page — an identity form (`AccountIdentityForm` in `forms.py`: username + email, `field_classes = {"username": UsernameField}` to match `UserCreationForm`'s validation) and a settings form (`AccountSettingsForm`, covering `log_retention_days`, `notify_on_push_error`, and `auto_end_broadcast_on_drop` — one card, one submit, since none of these is complex enough alone to justify its own view/URL the way e.g. chat settings vs. chat reset do), each its own `<form>` on the page distinguished by which submit button was pressed (`save_identity`/`save_settings` in `request.POST`) rather than by URL, since splitting them onto separate pages would be overkill for two small forms. PRG pattern (POST → `messages.success` → redirect) throughout, matching the rest of the app. Username changes apply immediately; email does not — `identity_form.is_valid()` mutates `request.user.email` in-memory as a side effect of validating against the bound instance, so `profile` explicitly reverts it back to the old value before saving, then (if the address actually changed) calls `send_email_change_confirmation` (link to `confirm_email_change`, token from `tokens.make_email_change_token`, sent to the **new** address — see `emails.py` below) and `send_email_change_alert` (heads-up to the **old** address) rather than writing the new email straight to the DB. `confirm_email_change` (`accounts:confirm_email_change`, no login required — the emailed link is the credential, and it's mailed to the new address, so the visitor clicking it may not be logged in as that account on this device/browser at all) follows the same GET-shows-confirmation/POST-applies two-step as `admin_decision` below, for the same reason: a one-shot GET-triggers-the-change link is vulnerable to email clients/antivirus tools prefetching links, which would silently apply the change with no human involved. Re-checks email uniqueness at confirm time (not just at request time) in case someone else claimed the address in the meantime. `ProfilePasswordChangeView` subclasses Django's built-in `PasswordChangeView` (already `login_required` internally) just to add a success message and redirect straight to `accounts:profile` instead of a separate "done" page. Linked from `crud/base.html`'s topbar (username is now a link, not plain text). `telegram_notify_toggle` and `telegram_unlink` are the Telegram-card counterparts to `destination_toggle`'s pattern (POST-only, flips/clears rather than taking the new value from the request body) — `telegram_unlink` clears both `telegram_chat_id` and `notify_telegram_on_push_error` together, not just the chat id, so a later re-link doesn't silently resurrect a stale notification preference. See `telegram_bot.py` below for how `telegram_chat_id` gets set in the first place. `register` creates an inactive `PENDING` user and emails admins, throttled per-IP the same way as login (`REGISTER_THROTTLE_LIMIT`/`_WINDOW` — a successful registration notifies every `is_staff` user, so an unthrottled endpoint is an admin-inbox spam vector, not just a form-abuse one); `admin_decision` handles the approve/reject link (GET shows a confirmation page, POST applies the decision) keyed by a signed token from `tokens.py` (`django.core.signing`, no login required to act on the link — the token itself is the credential, `max_age` bounds its lifetime). `ThrottledLoginView` wraps `LoginView` with a per-IP failed-attempt lockout (`LOGIN_THROTTLE_LIMIT`/`_WINDOW` constants, state in `django.core.cache` — default LocMemCache, so it's per-process; fine for the current single-worker deployment, won't share state across multiple gunicorn workers if that ever changes). All three throttles (login, register, password reset) key on `client_ip(request)`, not a bare `request.META["REMOTE_ADDR"]` — behind nginx (the only way this app is actually deployed, see docker-compose.yml notes below) `REMOTE_ADDR` is always nginx's own container IP, not the visitor's, so every real user would otherwise share one counter and one person's failed logins would lock out everyone else (confirmed live: same `REMOTE_ADDR` for requests carrying different `X-Forwarded-For` values). `client_ip()` trusts nginx's `X-Real-IP` header only when `REMOTE_ADDR` itself is a private/reserved address (Python's `ipaddress.is_private`, which covers RFC1918 *and* IANA special-purpose ranges) — i.e. only when the immediate connection came from inside the docker network — because `django`'s port is also published directly to the host (`8000:8000`) and a request hitting that port straight from the public internet could otherwise forge `X-Real-IP` to dodge the limit or frame another IP for it.
  - `emails.py` — sends the notification emails (new-registration to all `is_staff` users, approved/rejected to the applicant, plus the email-change pair below) via `django.core.mail.send_mail` + templates under `accounts/templates/accounts/email/`. `send_email_change_confirmation` goes to the **new** address (proves its owner actually requested the change, not a typo or someone else's address) with the confirm link; `send_email_change_alert` goes to the **old** address at the same time, with no link (there's no cancel mechanism, just "if this wasn't you, change your password") — added specifically so a hijacked session changing the email doesn't happen invisibly to the account's actual owner.
  - `telegram_bot.py` — thin `urllib.request` wrapper around the Telegram Bot API (same style as `crud/youtube_chat.py`): `send_message(chat_id, text)` and `get_updates(offset, timeout)` (long polling — the `timeout` param tells Telegram how long to hold the request open server-side waiting for a new update, so the client-side `urlopen` timeout is set a bit higher than that, not the other way around). Both fail-soft to `False`/`[]` when `settings.TELEGRAM_BOT_TOKEN` is unset or the request errors, same pattern as `nginx_stat.py`/`nginx_control.py`. A bot can't message a user first — Telegram requires the user to `/start` it — so `telegram_chat_id` is only ever populated by `poll_telegram_bot` below reacting to that `/start`, never set directly from a form.
  - `tokens.py` also has `make_telegram_link_token`/`read_telegram_link_token` (`django.core.signing`, 15-minute `max_age` — short on purpose, since the token only needs to survive "open Telegram and tap Start"; an expired one is simply replaced by reloading the profile page, which regenerates it for free since it's a pure signing operation, no DB/network involved). `accounts.views.profile` builds the deep link as `https://t.me/<TELEGRAM_BOT_USERNAME>?start=<token>`.
  - `management/commands/poll_telegram_bot.py` — the project's second long-running process (see `poll_youtube_chat` under `crud/` below for the first; same shape: one infinite loop, started once by `docker-entrypoint.sh` in its own restart-on-crash shell loop). Calls `get_updates` in a tight loop with no explicit `sleep` between iterations — Telegram's own long-poll `timeout` on the `getUpdates` call is what paces it, so no busy-loop; the one exception is when `TELEGRAM_BOT_TOKEN` is unset, where it sleeps 30s between checks instead of calling an API that would return instantly and spin the CPU. On a `/start <token>` message, resolves the token via `read_telegram_link_token`, sets that user's `telegram_chat_id`, and replies with a confirmation — any other `/start` (missing/invalid token) gets an explanatory reply instead of being silently ignored. Wraps DB access in `_handle_update` with the same `OperationalError` → `connection.close()` recovery as `poll_youtube_chat`, for the same reason (a bare infinite-loop command never goes through Django's normal per-request connection-health checks).
  - Login/logout reuse Django's built-in `auth.views.LoginView`/`LogoutView` (the former subclassed as `ThrottledLoginView`, see above); a `PENDING`/`REJECTED` account simply can't log in because `is_active=False` until approved — no custom auth backend needed. Password reset also reuses Django's built-in `PasswordReset*View`s (`urls.py`) — each needs an explicit `success_url=reverse_lazy("accounts:...")` because their defaults resolve unnamespaced view names (`password_reset_done` etc.) that don't exist under this project's `app_name = "accounts"` namespacing and 404 otherwise. `PasswordResetView` is subclassed as `ThrottledPasswordResetView` (same per-IP cache pattern, `PASSWORD_RESET_THROTTLE_LIMIT`/`_WINDOW`) — counts every POST, not just ones for a registered email, since `PasswordResetForm` always responds the same way either way (deliberately, to not leak which emails exist), so "did it succeed" isn't a signal available here the way it is for login/register.
- `crud/` — two-level, owner-scoped RTMP configuration, plus the HTTP hooks nginx-rtmp calls:
  - `models.py` — `Stream` (an ingest point: `owner` FK to `accounts.User`, `name`, unique auto-generated `stream_key` shared by both protocols, `publish_server`/`srt_publish_url` properties built from `settings.RTMP_SERVER_HOST`/`RTMP_APP` and `settings.SRT_SERVER_HOST`/`SRT_PORT` respectively — either is `None` if its host setting is unset. `publish_server` deliberately excludes `stream_key` (`stream_detail.html` shows it as a separate "Ключ" field) — most encoders, OBS included, want "Server" and "Stream Key" as two fields to paste in, not one combined URL; `srt_publish_url` stays a single combined string since that's how SRT output fields are configured (one URL, `streamid=publish:<stream_key>` embedded as a query param, not a separate field anywhere). `expected_live` (`BooleanField`, default `False`) is intent, not current fact — set `True` by `on_publish_hook` on a successful publish (SRT-sourced streams get this too, since `srt-bridge/start.sh` republishes into nginx as an ordinary RTMP publish once the SRT leg is up, hitting this same hook) and cleared either by the user explicitly ending the broadcast (`crud:stream_end_broadcast`) or by `poll_stream_health` (see below) noticing the stream dropped without that happening — it exists specifically so the latter can tell "ended on purpose" apart from "ended without saying so", something nginx-rtmp's `/stat` alone can't do since it only ever answers "is it live right now", with no memory of intent; `Rtmp` (a restream destination: `stream` FK to `Stream`, social network name/viewing URL/RTMP link/RTMP key, `push_url` property = link+key joined for ffmpeg). `socialmedia_rtmp_key` is a real credential (the platform's stream key), so it's stored encrypted at rest via `crud.fields.EncryptedCharField` (Fernet, key in `settings.FIELD_ENCRYPTION_KEY`, separate from `SECRET_KEY` so one can be rotated without the other) — see `crud/fields.py`. Fernet isn't deterministic (same plaintext → different ciphertext each time), so there's no DB-level `unique`/`unique_together` on this field and no `.filter(socialmedia_rtmp_key=...)` anywhere; per-stream uniqueness is enforced in `Rtmp.clean()` by decrypting and comparing in Python — on the **model**, not in `DestinationForm`, because a form-level check is invisible to any other `ModelForm` built from this model, and Django admin builds its own (`RtmpAdmin` doesn't set `form =`); confirmed live that duplicates saved silently through `/admin/crud/rtmp/add/` before this moved to `Model.clean()` (which every `ModelForm`, admin's included, calls via `full_clean()`). `destination_create`/`destination_update` wrap the check+save in `transaction.atomic()` with `Stream.objects.select_for_update()` to close the race a DB constraint would otherwise have closed — admin's own add/change views aren't wrapped the same way, which is an accepted narrower gap (staff-only, not the main user-facing path). Migration `crud.0004_...` re-saves every existing row to encrypt values written before this field existed — safe to re-run/idempotent because `from_db_value` falls back to returning a value as-is (via `InvalidToken`) when it isn't a valid Fernet token, so reading pre-migration plaintext never crashes. `Rtmp.platform_badge` (property, matched by substring against `socialmedia_name` — free text, not a choice field) drives the colored circular initials-badge next to each destination on `stream_detail.html` — deliberately not the platforms' actual logos/SVGs (trademark-fidelity concerns not worth it for a decorative badge); unrecognized platform name falls back to its first letter on a neutral gray badge rather than erroring or showing nothing.
  - `views.py` (CRUD) — all require login (`@login_required`) and scope queries to the current user (`Stream.objects.filter(owner=request.user)`, `Rtmp` via `stream__owner=request.user`); accessing another user's object returns 404 rather than 403 to avoid leaking existence. `destination_log` (`crud:destination_log`) is the same pattern applied to log viewing — reads `crud/destination_logs.py`'s `read_destination_log(stream_key, destination_id)`, which just does a filesystem read against the shared `rtmp_logs` volume (see `rtmp-push/` above); no separate auth layer needed since the file path is built from already-owner-checked `Rtmp`/`Stream` fields, not raw request input. Tail-capped to the last 500 lines (`MAX_LINES`) to keep the page bounded regardless of how long a destination has been erroring/reconnecting. `destination_log_json` (`crud:destination_log_json`) is the same read wrapped as a JSON endpoint (`{"log_text": ...}`, same `None`/empty/text tri-state as the template) so `destination_log.html` can auto-refresh (`live_stats.js`'s `pollLog()`, 5s interval via `data-log-url`) while a destination is actively erroring/reconnecting, without the user manually reloading to see new lines. `destination_toggle` also sets a `messages.success` flash ("«name» включена/выключена") on top of flipping `Rtmp.enabled` — otherwise the only feedback for a checkbox click was the switch itself silently changing state, easy to miss if the click also scrolled or if the switch is below the fold. `index` attaches a `.live_status` dict (`{"live": bool, "push_error": bool}`, via the shared `_stream_live_status()` helper) to each `Stream` instance in Python before rendering, rather than computing it in the template, so `index.html` can badge each of a user's streams live/offline (plus an "ошибка пуша" badge, same `.badge.error` class the per-destination status badge already uses on `stream_detail.html`) right on first paint, same as `stream_detail` already did per-stream; `index_live_json` (`crud:index_live_json`) is the polling counterpart (`live_stats.js`'s `pollIndexLive()`, 5s interval via `data-index-live-url` on the `<ul>`) — `{"available": bool, "streams": {"<stream_id>": {"live": bool, "push_error": bool}, ...}}`, scoped to `request.user`'s own streams same as every other view here, `available: false` short-circuits to an empty `streams` map when `NGINX_STAT_URL` is unset rather than pretending every stream is offline. `push_error` is `True` only when the stream is currently live *and* at least one of its `enabled` destinations has `push_status == "error"` — same staleness guard as the per-destination badge on `stream_detail.html` (`_stream_stats()`): without gating on `live`, a destination's stale "error" from a session that ended uncleanly (nginx crash before it could report the real end state) would keep the main list showing a false alarm indefinitely, since nothing else ever clears `push_status` back to unknown. `destination_create`/`destination_update` also pass `presets=DESTINATION_PRESETS` (see `destination_presets.py` below) into `destination_form.html`'s context so the platform-picker dropdown has something to render. `destination_test_push` (POST-only, owner-checked) and `stream_test_push_all` (same, but for every `enabled` destination on a stream at once) wrap `crud.destination_test.test_push`/`test_push_many` (see below) and surface the result via the same per-destination `messages.success`/`messages.error` pattern `destination_toggle` already uses — `stream_test_push_all` just does it once per destination in a loop instead of once.
  - `views.py` (infra hooks, called by nginx/`rtmp-push`/MediaMTX, not browsers — all under the `rtmp-hooks/` URL prefix even though `srt_auth_hook` now lives there too) — `on_publish_hook` (`crud:on_publish_hook`) validates a stream_key on RTMP publish start (200/403) and, in the same `.update()` query, sets `Stream.expected_live = True` (see `models.py` above and `poll_stream_health` below); `stream_destinations_hook` (`crud:stream_destinations_hook`) returns a JSON list of `push_url`s for `rtmp-push/push.sh` to relay to (only `Rtmp.enabled=True` destinations — the per-destination toggle switch on `stream_detail.html`, `crud:destination_toggle`, POST-only, owner-checked, just flips the field; like the rest of the destination list, only takes effect on the next publish start, not a currently-live one — see the restart hint on that page); `srt_auth_hook` (`crud:srt_auth_hook`) is MediaMTX's `authHTTPAddress` target — JSON body (not form-encoded like the others), always allows non-`"publish"` actions, validates `path` against the DB for `"publish"`; `destination_status_hook` (`crud:destination_status_hook`) is `rtmp-push/push.sh`'s callback for per-destination push status (see `rtmp-push/` below) — fetches the `Rtmp` row (rather than a bare `.update()`) specifically to compare against the *previous* `push_status` before overwriting it: only an edge transition into `"error"` (not already `"error"`) triggers `crud.emails.send_push_error_email` (when `destination.stream.owner.notify_on_push_error` is set) and independently `crud.telegram_alerts.send_push_error_telegram` (when `notify_telegram_on_push_error` is set — see `accounts/` above; the two are separate opt-ins, not a single channel choice, so both can fire on the same edge transition) — otherwise a stuck reconnect loop reporting "error" over and over would notify the user once per retry instead of once per incident; recovering (`"live"`) and erroring again resets the edge, so a second real incident notifies again. All four require `?secret=` to match `settings.RTMP_HOOK_SECRET` via `hmac.compare_digest` (not `==` — constant-time, avoids a timing side-channel on the shared secret) (shared across RTMP and SRT infra; empty secret = always reject, fail closed).
  - `nginx_stat.py` — `fetch_stream_stats(stream_key)` pulls and parses nginx-rtmp's `/stat` XML (`settings.NGINX_STAT_URL`, empty = skip and return `None` — e.g. bare dev with no nginx running). Returns `None` (unavailable), `{"live": False}` (not currently streaming), or live byte/bitrate/uptime counts plus (`_parse_meta`) the incoming stream's own technical parameters — resolution, frame rate, video codec, audio codec/channels/sample rate — read from nginx-rtmp's `<meta>` block in `/stat` (nginx itself parses this from the publisher's `onMetaData`/codec headers, not something this project computes). Keys are simply absent from the dict (not `None`) when `<meta>` isn't there yet — briefly true right after publish start, before nginx has had a chance to parse it — so template/JS only need one falsy check (`stats.video_codec`), not a None-vs-missing distinction. Used by `stream_detail` to show per-stream status and, when present, this media info as a second row under the byte/bitrate stats. `fetch_live_stream_keys()` fetches the same `/stat` XML **once** and returns a `set()` of every currently-live `stream_key` (or `None` under the same unavailable/unreachable conditions as `fetch_stream_stats`) — used by `index`/`index_live_json` to badge a user's whole stream list without one `/stat` round-trip per stream (an N+1 `fetch_stream_stats()`-per-row call would have been the naive alternative).
  - `server_load.py` — `get_server_load()`: `os.getloadavg()` (always available on Linux/macOS), memory % from `/proc/meminfo` and disk % from `shutil.disk_usage("/")` (both `None` if unreadable, e.g. no `/proc` outside Linux — degrades per-metric, not as an all-or-nothing block). Used by `index` for a "server load" panel; inside the Docker containers this reflects real container/host figures, on bare macOS dev memory is `None` but load/disk still populate.
  - `nginx_control.py` — `restart_stream(stream_key)` calls nginx-rtmp's control module (`GET /control/drop/publisher`, `settings.NGINX_CONTROL_URL` + `settings.RTMP_APP`, empty URL = unavailable, same fail-closed pattern as the other nginx integrations) to forcibly disconnect the current publisher. This is a full reset, not a relay-only restart — it only "restarts the broadcast" if the streaming client (OBS etc.) auto-reconnects, which then runs the normal `on_publish`/`exec_publish`/`push.sh` cycle again (picking up any destination changes). `crud:stream_restart` is the login-required, owner-checked, CSRF-protected view wiring this to a button on `stream_detail`; result surfaces via `django.contrib.messages` (first use of that framework in the project — already configured, just unused before). `stream_delete` calls the same `restart_stream()` right after deleting the row — confirmed live that without it, a publisher nginx had already accepted keeps relaying to every destination completely unaffected by the DB delete (nginx never re-checks a live publish against the DB mid-stream; only a *new* publish attempt hits `on_publish_hook` and gets rejected), so "delete" alone didn't actually stop an in-progress broadcast. `crud:stream_regenerate_key` (POST-only, owner-checked, on a button next to the key field on `stream_detail.html`, guarded by a plain JS `confirm()` since it breaks any encoder already configured with the old key) is the same pattern for a leaked/compromised `stream_key`: it swaps in a fresh `Stream.stream_key` and then calls `restart_stream()` with the **old** key, not the new one — `restart_stream()` drops by `name=<stream_key>` against nginx's live publisher table, and any currently-connected publisher is still registered there under the old key at the moment the DB row changes, so dropping the new key would be a no-op and leave the old (supposedly revoked) key streaming until the client disconnects on its own. `crud:stream_end_broadcast` (POST-only, owner-checked, button on `stream_detail` shown only while the stream is live, JS `confirm()`-guarded) is the user-declared counterpart to a stream just dropping off unannounced: it clears `Stream.expected_live` **before** calling `restart_stream()`, not after — so if nginx-control happens to be unreachable and the drop itself fails, the flag is still correctly cleared and `poll_stream_health` won't mistake the (still pending) natural end of that session for an unannounced one.

Requires `ffmpeg` in the `django` image specifically for this (added to `Dockerfile` — the real relay ffmpeg processes still run in the `nginx` container via `rtmp-push/`, this isn't a duplicate relay path). `test_push_many(push_urls_by_id)` runs `test_push` concurrently over a `ThreadPoolExecutor` rather than sequentially — `subprocess.run` releases the GIL while waiting on the child process, so total wall time for "check all of a stream's destinations" stays bounded by one `TEST_PUSH_TIMEOUT_SECONDS`, not the sum across destinations.

Every `SCAN_INTERVAL` (30s) seconds, fetches `fetch_live_stream_keys()` **once** for all streams (same N+1-avoidance reasoning as `index`/`index_live_json` above) and diffs it against `Stream.objects.filter(expected_live=True)` — anything marked expected-live but absent from that set dropped without the user saying so via `crud:stream_end_broadcast`, so — unless the owner has `accounts.User.auto_end_broadcast_on_drop` set, in which case it's simply not their problem to be told about — it fires `crud.emails.send_stream_drop_email`/`crud.telegram_alerts.send_stream_drop_telegram` (same `notify_on_push_error`/`notify_telegram_on_push_error` opt-ins as push errors — a separate toggle for *channel* would've been one more checkbox for a conceptually similar "something about my stream broke" event; `auto_end_broadcast_on_drop` is a different axis, whether the event counts as notable at all, not which channel it goes through). Clears `expected_live` right after regardless of that toggle — the stream isn't live either way, so leaving the flag stale would be wrong even when nobody gets told about it, edge-triggered the same way `push_status` is, so a stream stuck offline doesn't get re-notified every tick. Skips the tick entirely (notifies nobody) when `fetch_live_stream_keys()` returns `None` — `/stat` being unreachable isn't the same as "every stream just dropped", and treating it that way would fire a false alarm to every user with `expected_live=True` at once. Collects the dropped rows into a plain list first, then updates by explicit `pk__in` rather than re-filtering the same queryset a second time — avoids a subtle race where a stream reconnecting (a fresh `on_publish_hook` setting `expected_live` back to `True`) between the `SELECT` and an equivalent `UPDATE ... WHERE expected_live=True AND ...` could get its just-set flag clobbered back to `False`.

Exist because both failure modes they catch otherwise pass an empty install silently and only surface later, cryptically: a missing/invalid `FIELD_ENCRYPTION_KEY` doesn't error until the first `Rtmp` row is actually read/written (`Fernet(...)` in `crud/fields.py` is only ever called lazily, not at import time), and an empty `ALLOWED_HOSTS` with `DEBUG=False` doesn't error until the first real request (Django only enforces it via `DisallowedHost` at request time, not at startup) — which for this project includes the nginx/srt hooks, so it silently breaks 100% of publishing, not just the web UI. Added after a real deployment (hand-rolled `docker-compose.yml` instead of using `docker-compose.prod.yml`) hit both blind.

- `nginx/` — Docker image for nginx-rtmp (not installable as a stock package; built from `debian:bookworm-slim` + the `libnginx-mod-rtmp` apt package, which bundles both the stat and control sub-modules — no separate module needed for `/control`). `nginx/conf/nginx.conf.template` is rendered by `nginx/docker-entrypoint.sh` via `envsubst` (`DJANGO_HOOK_BASE_URL`, `RTMP_HOOK_SECRET` env vars) before nginx starts. Build from the **repo root** (not `nginx/`) so the build context includes `rtmp-push/`: `docker build -f nginx/Dockerfile -t restream-nginx .`. Deliberately `worker_processes 1` — nginx-rtmp connections/stats aren't shared across workers, so `/stat` on a multi-worker setup only reflects whichever worker handled a given request. The internal `server { listen 8080; }` block hosts both `/stat` and `/control` (`rtmp_control all;`) — not published beyond `127.0.0.1` on the host, same trust boundary for both. `nginx/docker-entrypoint.sh` also `chmod 1777`s `/tmp/rtmp-push` (the `rtmp_logs` volume's mount point, see `rtmp-push/` below) before starting nginx — that path is now a named Docker volume, not a plain `/tmp` subdirectory, and Docker initializes a fresh volume's root as `root:root 0755`; `exec_publish`/`exec_publish_done` (`push.sh`/`stop.sh`) run as the nginx worker's user (`www-data`, not root — `user www-data;` above), so without this fix `push.sh`'s first line (`mkdir -p "$PID_DIR"`) fails `Permission denied` and the *entire* restream-out mechanism silently stops working — not just log viewing. Confirmed live on a real deployment: nginx's own log showed `exec: child '/rtmp-push/push.sh' started` immediately followed by `exited with code 1`, no error visible anywhere else (default nginx `error_log` level doesn't surface either line — had to temporarily bump to `debug` to see it at all). A real regression from introducing the `rtmp_logs` volume for `crud:destination_log`, not a pre-existing issue.
- `rtmp-push/` — `push.sh`/`stop.sh`, invoked by nginx-rtmp's `exec_publish`/`exec_publish_done` (not run directly). `push.sh` fetches the destination list from `stream_destinations_hook` and launches **one `ffmpeg -c copy` process per destination** (not one process with N `-f flv` outputs — confirmed live that ffmpeg aborts the *entire* process if it can't open even one of several outputs, which was silently killing delivery to every destination whenever just one was unreachable), tracking each PID at `/tmp/rtmp-push/<stream_key>/<destination_id>.pid` (and its own `<destination_id>.log`, kept around after the stream ends — only the `.pid` is removed — so a failed destination is still debuggable after the fact; a subsequent publish for the same `stream_key` just overwrites the same destination-keyed files). Filenames are keyed by the destination's DB id (not its position in the list) so they stay stable regardless of destination order/count between publishes — `crud:destination_log` (see below) depends on this being a fixed, predictable key. This dir is a named Docker volume (`rtmp_logs`, see `docker-compose.yml` below) shared into the `django` container at `/rtmp-logs` — not read-only, since `crud/management/commands/cleanup_destination_logs.py` (run hourly by `docker-entrypoint.sh` in the background, plus once at container start) needs to delete stale `*.log` files there; it only ever touches `.log`, never `.pid`, on purpose — `.pid` bookkeeping is `push.sh`/`stop.sh`'s alone, Django doesn't get to touch a live process's control file. For a still-existing destination, retention is its owner's `accounts.User.log_retention_days`; for an orphaned file (destination or whole stream already deleted from the DB — nobody left to own a retention setting) it falls back to `accounts.models.DEFAULT_LOG_RETENTION_DAYS`, which also incidentally fixes the "deleted destination's log lingers forever" gap this file layout used to have. `crud:destination_log`'s template shows the current retention via `crud/templatetags/ru_plural.py`'s `ru_days` filter — Django's built-in `|pluralize` only handles English-style singular/plural and silently renders empty for the 3-way Russian день/дня/дней (confirmed live), so this is a real custom filter, not decoration. Builds the ffmpeg argv via `set --` rather than `eval`/`sh -c` on purpose — destination URLs/keys come from user input (`Rtmp` fields) and must never be shell-interpreted (command injection). `stop.sh` sends TERM then polls `kill -0` for up to 5s before escalating to KILL, logging if it had to, for *each* per-destination process — nginx-rtmp doesn't force-close the push ffmpeg's read side when the publisher disconnects (it just goes idle), and a plain TERM confirmed live to sometimes never take effect, leaving the process stuck with an established connection to the destination indefinitely (discovered via live end-to-end testing with a real destination listener, reproduced twice). Each destination also gets its own background subshell in `push.sh` that reports live/error/stopped status back to Django (`crud:destination_status_hook`, `?destination_id=&status=`) — `Rtmp.push_status`/`push_status_at`, surfaced as a badge next to the destination's name on `stream_detail.html`, but **only while the stream itself is live** per nginx's `/stat` (guards against a stale "live"/"error" badge lingering in the DB from a session where nginx died uncleanly before it could report the real end state — Django has no other way to know the push processes' live status, unlike the stream-level badge which re-queries `/stat` fresh on every page load). The subshell distinguishes "stopped" (its own ffmpeg was killed by `stop.sh` — `wait` returns exit code 143/137, a signal) from "error" (ffmpeg exited on its own for any other reason — couldn't connect, or the destination dropped the connection mid-stream) purely from the exit code, no extra signaling needed between `push.sh` and `stop.sh`. `stream_destinations_hook`'s JSON now includes each destination's `id` (not just `push_url`) so `push.sh` has something to key status reports on.
- `srt-gateway/` — Docker image for SRT ingest, built on `bluenviron/mediamtx` (pinned release binary — `MEDIAMTX_VERSION` build arg in `srt-gateway/Dockerfile`, downloaded from GitHub releases for `$TARGETARCH`, not installable as a stock package either) + `ffmpeg`. **Key design point**: SRT is not a parallel stack with its own destinations/stats/restart — MediaMTX is just an alternate front door into the *same* RTMP ingest nginx already has. A client publishes SRT with `streamid=publish:<stream_key>` (same `stream_key` as RTMP — one ingest point, either protocol); MediaMTX's `authHTTPAddress` hits `crud:srt_auth_hook` (validates `action=="publish"` against the DB, same `RTMP_HOOK_SECRET`, always allows non-publish actions since our own bridge's internal read would otherwise get gated too); `paths.all_others.runOnReady` launches `srt-bridge/start.sh`, which reads the stream back from MediaMTX's own built-in RTMP re-exposure (`rtmp://127.0.0.1:1935/<path>`) and republishes with `-c copy` into nginx's `rtmp://nginx:1935/live/<stream_key>` — from that point on it's an ordinary RTMP publish and 100% of the existing pipeline (`on_publish_hook`, `push.sh`, destinations, `/stat`, restart) applies unchanged, no SRT-specific code anywhere downstream.
  - `srt-bridge/start.sh` runs in the **foreground** (`exec ffmpeg ...`, no backgrounding/PID file) — MediaMTX manages its lifecycle directly and sends it a stop signal when the path stops being ready (visible as "runOnReady command stopped" in `srt-1` logs), so there's no `stop.sh` needed (unlike `rtmp-push/`, where nginx's `exec_publish`/`exec_publish_done` are two separate hooks). `runOnReadyRestart: yes` in `srt-gateway/conf/mediamtx.yml.template` auto-relaunches the bridge if it fails to connect on the first try. **Do not turn `start.sh` into a backgrounding script again** — combined with `runOnReadyRestart` that caused MediaMTX to relaunch it every few seconds while the old ffmpeg process kept running in the background, spawning duplicate publishers (discovered live: repeated "runOnReady command exited: code 0" every ~5s in `srt-1` logs).
  - `-probesize 5000000 -analyzeduration 5000000` on the bridge's ffmpeg input are required, not cosmetic — MediaMTX's RTMP re-exposure of a freshly-ingested SRT stream doesn't carry a reliable `onMetaData` (unlike a normal OBS→RTMP publish), so ffmpeg's default probing intermittently fails to determine codec parameters in time and the relay to nginx never completes before a short-lived stream ends. Confirmed via live testing: without these flags, short streams reliably failed to relay (`Cannot open connection tcp://nginx:1935`); with them, short streams relay correctly.
  - Exact `runOnReady`/`authHTTPAddress` config key names were verified against the pinned MediaMTX version's own shipped `mediamtx.yml` (`docker run --rm <image> cat /mediamtx.yml`, or the raw file at that exact git tag) rather than assumed — MediaMTX has renamed hook directives across versions (older docs/AI summaries may reference `runOnOnline`/`runOnOffline` or `runOnPublish`, which do **not** exist in the pinned version). Re-verify against the shipped config if `MEDIAMTX_VERSION` is ever bumped.
  - **Known limitation**: `crud:stream_restart` (see `nginx_control.py` above) drops the RTMP-facing leg (the bridge) for SRT-sourced streams, not the original SRT connection at MediaMTX — the source stays connected there, but the relay into nginx won't come back until the SRT client itself reconnects. No MediaMTX-side "kick" is wired up (no API endpoint for this was confirmed reliable enough to implement blind).

Both now `logger.warning(..., exc_info=True)` before returning the same fallback value — behavior is unchanged, only observability.
- `Dockerfile`/`docker-entrypoint.sh` (repo root) — the Django image (`python:3.13-slim` + Poetry, `POETRY_VIRTUALENVS_CREATE=false`, `poetry install --without dev` so the `black` dev-group dependency never ships in the image; also installs `ffmpeg` via apt, needed only for `crud.destination_test`'s test-push feature — the real relay ffmpeg processes run in the `nginx` container via `rtmp-push/`, this is not a second relay path). The entrypoint waits for Postgres to accept connections (plain `depends_on` only waits for container start, not DB readiness), then runs `migrate`, `collectstatic`, `cleanup_destination_logs` once, spawns a background `while true; do sleep 3600; cleanup_destination_logs; done` loop (no Celery/task-queue in this project — this is the entire scheduler), spawns `poll_youtube_chat`, `poll_telegram_bot`, and `poll_stream_health` each in its own restart-on-crash background loop (see `crud/` → Multi-chat, `accounts/` → `poll_telegram_bot`, and `crud/` → `poll_stream_health` above — unlike the cleanup loop, these run forever rather than being re-invoked periodically), and finally `runserver 0.0.0.0:8000`. `.dockerignore` excludes `.env` — never remove that exclusion, `COPY . .` would otherwise bake secrets into the image layer.
- `docker-compose.yml` — `db` (`postgres:16-alpine`, not exposed to the host to avoid clashing with a locally-running Postgres on 5432), `django` (builds the root `Dockerfile`; its `8000` is published as `127.0.0.1:8000:8000`, not `8000:8000` — nginx reaches it at `http://django:8000` over the compose network regardless of host port publishing, so this is purely for local `curl localhost:8000` convenience; publishing to `0.0.0.0` would let anyone reach Django directly on a real server, bypassing nginx and its `Cache-Control` — this is also why `accounts.views.client_ip()` can't blindly trust `X-Real-IP`, see above), `nginx` (builds `nginx/Dockerfile`, now also reverse-proxies HTTP: a second `server { listen 80; }` block in `nginx/conf/nginx.conf.template` proxies `/` to `http://django:8000` and serves `/static/` directly from a shared `static_files` volume populated by `collectstatic`; also writes `rtmp-push/push.sh`'s per-destination logs to the `rtmp_logs` volume at `/tmp/rtmp-push`, also mounted into `django` at `/rtmp-logs` — read/write there, not read-only, see `rtmp-push/` above for why), `srt` (builds `srt-gateway/Dockerfile`, exposes `8890/udp`). nginx's/MediaMTX's hooks reach Django at `http://django:8000` — Django's `ALLOWED_HOSTS` gets `django` appended in compose (see the `.env` note above) since that hostname never appears in the browser-facing `Host` header. `RTMP_SERVER_HOST`/`SRT_SERVER_HOST` (the *public* addresses shown to users) are deliberately **not** overridden in compose — they come straight from `.env`, same as on bare metal, since they mean something different (the box's public hostname/IP) than the compose-internal service hostnames used elsewhere in this file.
- **Docker Hub publishing**: all three custom images (`Dockerfile`, `nginx/Dockerfile`, `srt-gateway/Dockerfile`) carry an OCI `LABEL` block (`org.opencontainers.image.title`/`description`/`source`/`documentation`/`licenses="MIT"`, matching the root `LICENSE` file). `.github/workflows/docker-publish.yml` builds and pushes all three as `damodara/restreambyddas-{django,nginx,srt}` on git tags matching `v*` (multi-arch `linux/amd64`+`linux/arm64` via `docker/setup-qemu-action`+`buildx`, tagged both `latest` and the exact version). Requires repo secrets `DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN` (a Docker Hub access token, not the account password) added manually in GitHub — not something CI or this file can provision. `docker-compose.prod.yml` mirrors `docker-compose.yml` but with `image: damodara/restreambyddas-*:${TAG:-latest}` instead of `build:`, so a server only needs that file + `.env` (no repo checkout) to run a published release — see README.md → "Docker Hub" for the exact commands. `docker/README.{django,nginx,srt}.md` hold the per-image Docker Hub description text, but CI deliberately does **not** sync them automatically (a `peter-evans/dockerhub-description` step was tried and removed) — Docker Hub's repository-description Hub API (`PATCH /v2/repositories/...`) reliably returns `Forbidden` for a personal access token regardless of its scope (confirmed live: still failed after regenerating the token with Read/Write/Delete), a known unresolved Docker Hub limitation, not a config mistake on this repo's side. Paste the file contents into the repository's Docker Hub description field by hand instead.
